## 1. Цель
Выиграть хакатон (Zhambyl hub), кейс: «Data-Driven Curriculum: интеллектуальная система оценки эффективности учебников и учебных программ». Задача по тексту кейса: EdTech-платформа для методистов, которая (а) анализирует результаты тестирования школьников по темам программы, (б) выявляет сложные для усвоения разделы, (в) сравнивает эффективность учебников, (г) формирует обоснованные рекомендации по распределению учебных часов. Главная ценность по кейсу: переход от субъективных решений к решениям на измеримых образовательных результатах.

Как мы выигрываем: рабочее демо на правдоподобных данных, честная статистика (не обёртка над LLM), объяснимость каждой рекомендации, понимание реальных норм РК и аккуратные формулировки.

## 3. Ограничения реальности (из отчёта, соблюдать в продукте и текстах)
- **Что можно рекомендовать по часам.** Нормы фиксируют недельную нагрузку по предмету (ТУП). Внутри раздела и темы часы распределяет учитель, КТП он составляет раз в год. Пределов «±N часов» и «резервных часов по приказу» в нормативке не найдено. Поэтому рекомендация формулируется так: «рекомендуемое распределение часов по темам внутри раздела при неизменной недельной нагрузке, основа для КТП учителя». Нельзя писать «разрешено перераспределять N часов», «утверждает завуч» как норму, «используйте вариативный компонент».
- **Сравнение учебников.** Внутри школы невозможно (один учебник на параллель), возможно только межшкольное, и только по предметам, где в Перечне 2–3 альтернативы (физика 7–9, казахский язык 5–9, алгебра и геометрия, история Казахстана, математика 5–6). Выбор делается один раз и в апреле (методсовет до 10 апреля), поэтому отчёт должен быть готов к заседанию методсовета.
- **Вход данных.** СОР и СОЧ в 2–4 классах с 1.09.2026 заменены промежуточным оцениванием, в 5–11 суммативное оценивание за раздел пока сохраняется, а отмена в 2027–2028 только заявлена. Схема входа не должна зависеть от типа работы: единица данных «ученик × работа × задание × балл / максимум». Реальные выгрузки Kundelik и BilimClass по заданиям не подтверждены, поэтому основной вход это CSV/Excel.
- **Персональные данные.** В демо только синтетика, помеченная баннером «Синтетические данные». Реальные ФИО и ИИН платформа не принимает. Для пилота: случайный токен вместо идентификатора, таблица соответствий остаётся в школе, хранение в РК. Это не юридическое мнение, нужна проверка юриста.
- **Дисциплина формулировок.** Не писать «учебник причиняет результат». Писать «разница учебников с поправкой на уровень учеников и школы», всегда с интервалом, и при нехватке данных показывать «Недостаточно данных для утверждения». Про конкурентов говорить «в прочитанных материалах не найдено», а не «у них нет».

## 4. Что строим (MVP)
Модули, по порядку важности:
1. **Импорт.** Загрузка CSV/Excel в схеме `results_long.csv`, валидация (типы, ограничения, пропуски), отчёт о качестве данных, понятные сообщения об ошибках.
2. **Сложность тем.** Индекс сложности и дискриминативность заданий, агрегация по темам, пометка «плохих» заданий (чтобы тема не казалась сложной из-за плохих вопросов). Дальше: калибровка IRT с якорными заданиями для сравнимости разных работ.
3. **Сравнение учебников.** Смешанная модель с случайным эффектом школы, входным уровнем ученика, средним входным уровнем школы (подход Mundlak), языком обучения, типом местности и стажем учителя; взаимодействие учебник × тема. Вывод: оценка, интервал, число школ, метка «недостаточно данных». Рядом показывать наивное сравнение, чтобы было видно парадокс Симпсона.
4. **Рекомендации по часам.** Оптимизация с фиксированной суммой часов, границами min/max по теме и убывающей отдачей. Отдача на тему калибруется по данным (вариация часов между классами), а не берётся с потолка. Результат подаётся как сценарий с диапазоном и неопределённостью (bootstrap), а не как «оптимальное решение». Известная ловушка: сложность тут нужно умножать на прирост, а не делить (иначе оптимизатор отдаст часы лёгким темам); после округления границы min/max должны сохраняться (метод наибольших остатков с ремонтом границ).
5. **Объяснимость.** У каждой рекомендации кнопка «Почему?»: на каких данных, какой метод, число школ и учеников, интервал, ограничения.
6. **Отчёт для методсовета.** Экспорт PDF и DOCX на русском и казахском. LLM только превращает JSON с цифрами в текст, ничего не считает. Без ключа API работает шаблонный текст. Казахскую версию должен проверить носитель языка.

Не делаем: чат-бот для учителей, авторизацию, оплату, мобильное приложение, всё, чего нет в кейсе.

## 5. Архитектура
```
CSV/Excel -> [validate/import] -> [difficulty] -> [textbooks mixed model] -> [hours optimizer]
                                       |                  |                      |
                                       +---------- JSON результатов -------------+
                                                          |
                                        [report: шаблон или LLM] -> PDF/DOCX
                                                          |
                                                [UI: тепловая карта, сравнение, сценарии]
```
- Ядро аналитики в отдельном Python-пакете без зависимости от UI (чтобы тестировать и переиспользовать). Эндпоинты: `/import`, `/analyze/difficulty`, `/analyze/textbooks`, `/optimize/hours`, `/report`.
- Модули не читают `ground_truth.json`. Он нужен только тестам и блоку валидации.
- Все параметры (пороги «недостаточно данных», границы часов, доверительный уровень) вынести в конфиг. Пороги вроде «меньше 10 школ» это допущение, а не норматив; по литературе для смешанных моделей ориентир около 50 групп, при 10 группах интервалы ненадёжны.

## 6. Экраны для демо
1. Загрузка файла и отчёт о качестве данных.
2. Тепловая карта «тема × школа/учебник», цвет — освоение; список топ-проблемных тем.
3. Сравнение учебников: наивное и с поправкой рядом, интервалы, метки «недостаточно данных».
4. Сценарий часов: ползунки «до/после», прогноз с диапазоном, кнопка «Почему?».
5. Экспорт записки (RU/KZ), переключатель языка интерфейса.

Сценарий демо на 3 минуты: загрузил файл, нашёл три проблемные темы, показал, что наивный отчёт выбрал бы учебник A, а модель показывает, что он слабее, получил рекомендацию по часам, скачал записку. Подготовить два набора данных: основной и маленький «на случай сбоя».

## 7. Проверка качества (обязательно)
- Тесты (pytest): воспроизводимость на seed 2026; интервалы накрывают истину на 15 seed; наивная модель ошибается, модель с поправкой нет; ранговая корреляция сложности тем не ниже 0,7; оптимизатор сохраняет сумму часов и границы; импорт отвергает некорректные файлы.
- Добавить в генератор сценарий, где часы зависят от сложности темы (в реальных школах трудным темам дают больше часов), и проверить, как это ломает калибровку кривой «часы → освоение». Результат честно показать в отчёте.

## 9. Что сказать в питче (материал для слайдов)
- Проблема: учебник и часы выбирают на глаз, оценка учебников опирается на экспертизу и опросы, а не на результаты учеников (найдено в источниках, но это не доказательство отсутствия других оценок).
- Решение: статистика с поправкой на контекст школы + оптимизация часов + объяснимость.
- Доказательство: на синтетике с известной истиной наивное сравнение ошибается в 11 из 15 случаев, модель с поправкой попадает в 15 из 15.
- Честность: проверено на симуляции, дальше нужен пилот; список проверок для школы и отдела образования есть в отчёте.
- Кто платит: управление образования, РНП ЦЭСО, районные отделы (гипотеза, не подтверждена закупками).
